# STATE_INDEX_PLAN — parabula-next

Status: planning/index document only. No existing STATE file is moved, deleted, or rewritten by this document.

## Purpose

Create a safe plan for organizing and interpreting the 156 existing `STATE/*` files without losing historical evidence or confusing old reports with current truth.

## Core problem

`STATE/*` contains current reports, historical reports, generated reports, audits, decisions, open gates, and superseded information. Future AI sessions must not treat every STATE file as equally current.

## Status labels

| Label | Meaning |
|---|---|
| CURRENT | Current source of truth or current active status. |
| HISTORY | Historical evidence; useful but not current authority. |
| DECISION | A decision record that explains why something is the way it is. |
| AUDIT | Report produced by audit/check process. |
| VALIDATION | Report produced by validator or runtime probe. |
| OPEN_GATE | Known incomplete area or required future validation. |
| GENERATED | Generated by script/workflow. |
| SUPERSEDED | Replaced by newer file or live code, kept for context. |
| UNKNOWN | Needs review before use. |

## Authority rule

A STATE file can inform future work, but it cannot override:

- `meta/topics.json` for current metadata;
- root `עמוד-N.html` for current worksheet content;
- `styles/pages/עמוד-N.css` for current page CSS;
- `mobile-app.*` for current canonical mobile runtime;
- `preview/print.*` for current print runtime.

If a STATE file contradicts live canonical code, classify the conflict before acting.

## Superseded examples to watch

- Reports that describe page 95 as SVG/overlay while current page 95 is live HTML/MathJax.
- Mobile reports that compare against `mobile-topics.json` when canonical runtime now uses `meta/topics.json`.
- App-layer checks that treat `preview/phone.*` as canonical mobile.
- Reports expecting generated audit files to be committed when policy may define them as artifact-only.

## Indexing process

1. List all `STATE/*` files.
2. Extract date hints from filename/content.
3. Detect related area: mobile, print, equations, rules, preview, metadata, workflow, recovery.
4. Determine whether each file is current, historical, generated, validation, or open gate.
5. Mark whether it can be used as current authority.
6. Mark conflicts with live code.
7. Review before using any STATE file to justify cleanup.

## Do not do yet

- Do not move STATE files physically.
- Do not delete old STATE files.
- Do not rewrite history files.
- Do not treat unknown STATE files as current truth.

## Success condition

Future AI sessions can open `STATE/STATE_INDEX.md` and immediately know which STATE files are current, historical, generated, or superseded.
